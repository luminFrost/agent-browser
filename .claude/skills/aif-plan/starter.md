# 개발 스타터: 목표 정의 (기획)

## 규모 예시 (개발)
- **S** (30분 안팎): 커밋 1~2개. 새 의존성·스키마 변경 없음. 버그 하나, 간단한 API 하나·함수 하나, 문구·스타일, 기존 함수에 테스트 추가.
- **M** (2시간 안팎): 화면 하나나 작은 앱, API 몇 개, 새 의존성 한두 개. 한 사람이 한 번에 머리에 담을 수 있다. 예: 로컬 사용량 대시보드.
- **L**: 여러 모듈·데이터 모델 변경·외부 연동·인증·결제·마이그레이션. 구조 결정이 여러 개.

## 작업 카드 (S)
```
상태: 초안 | 승인
목표: (한 줄)
완료 기준:
- [ ] (재현 → 고쳐졌다는 관찰. 예: "빈 입력에 오류 문구가 뜨는 테스트가 통과")
확인 방법: (config.commands의 명령 또는 직접 확인 절차)
```

## 목표 문서 (M)
`spec.md`에서 가치, 범위(한다·안 한다), 요구사항과 인수 사례, 확인 방법, 검증 강도만 채운다. 나머지 칸은 비워 둔다. 질문은 빠진 것만 3개까지.

## 인터뷰 (L) — 한 번에 하나씩, 이 순서로
1. **가치:** 누가, 왜, 어떻게 써서, 무엇을 얻나 (한 문장)
2. **범위와 안 할 것**
3. **인수 사례:** "~하면 ~된다" 형식. 정상, 경계, 오류를 각각 하나 이상. 이것이 완료 기준이고, 개발 때 실패하는 테스트로 바뀐다.
4. **확인 방법:** 변형 파일의 "기획에서 물을 것"을 함께 묻는다.
5. **정본:** spec인가, 기존 코드인가
6. **상한:** 시간, 토큰. 완료 기준이 아니라 멈춤 신호다. spec의 "상한" 절에 쓰고 "제약"에 넣지 않는다.
7. **위험:** 실제 데이터, 결제, 인프라, 공개 계약에 닿나 → 닿으면 배포 단계의 되돌리는 방법을 지금 정한다.
8. **확인 필요:** 아직 추정인 것과 그것이 영향을 주는 곳

`config.roles`에 켜진 역할이 있으면 해당 역할의 기획 입력을 더한다.
- `qa`: 위험도(P0~P3), 테스트 설계 초안
- `backend`: 데이터 규모, API 계약 초안
- `frontend`: 화면 흐름, 상태 목록(로딩, 빈 상태, 오류)

## 목표 문서
`docs/spec.md`에 쓴다. 양식은 `.aif/framework/templates/spec.md`.
되돌리기 어려운 구조 결정이 있으면 `docs/design.md`와 `docs/adr/`도 쓴다.
