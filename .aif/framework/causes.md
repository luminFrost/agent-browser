# 원인 판정 기준

`/aif-report`에서 AI 판정에 쓰는 기준입니다. 판정자는 이 파일과 후보 파일(`ai-candidates.json`)만 보고 판정합니다.

## 무엇을 판정하나
후보 파일에는 세 종류가 있습니다.
1. **사람 메시지 분류:** 사람의 프롬프트가 아래 중 무엇인가
   - `approval`: 목표·전달을 승인함
   - `correction`: 결과를 고쳐 달라고 함
   - `stop`: 멈추게 함
   - `revert`: 되돌리게 함
   - `direction_change`: 목표·범위를 바꿈
   - `new_request`: 단순 추가 요청
   - `other`
   - `correction`이면 `topic`(무엇을 고치라는지 짧은 명사구)을 붙인다. 같은 주제가 몇 번 반복됐는지 세는 데 쓴다.
2. **완료 보고 판정:** AI의 턴 끝 문장이 무엇인가
   - `done_claim`: "끝났다/됐다"는 완료 보고
   - `stop_report`: 진행을 멈추고 원인이나 막힌 점을 보고함
   - `other`
   - 같은 턴에 확인 명령을 돌렸는지는 후보의 `check_runs_in_turn`에 있다. 판정자는 문장 종류만 고른다.
3. **원인 단계:** 코드가 찾은 문제·지연 항목마다 원인이 어느 단계인가

## 원인 단계 정의 (하나만 고른다, 위에서부터 차례로 확인)
| 순서 | 원인 | 이렇게 판단한다 | 이런 것은 아니다 |
|---|---|---|---|
| 1 | `plan_gap` 기획 누락 | 문제의 원인이 목표 문서·카드에 **없었던** 요구, 완료 기준, 질문, 제약이다. 또는 "확인 필요"로 남긴 항목이 실제로 문제를 만들었다 | 목표 문서에 있었는데 지키지 않은 것 (→ 설정 또는 구현) |
| 2 | `decision` 의사결정 지연·번복 | 사람이 결정을 늦게 했거나(대기), 승인 뒤 결정을 바꿨다(번복) | AI가 결정을 잘못 내린 것 (→ 구현 또는 설정) |
| 3 | `setting` 설정 문제 | 규칙·권한·훅·확인 명령·맥락(문서 위치, 데이터 의미)이 없거나 잘못 놓여서 AI가 몰랐거나 못 했다. 또는 규칙이 있었는데 AI가 반복해서 어겼다(→ 강제 수단이 필요) | 규칙을 한 번 어긴 실수 (→ 구현) |
| 4 | `process` 진행 방식 | 작업 크기, 세션 나누기, 검증 시점, 경로 선택이 원인이다. 예: 압축 반복, 가벼운에서 올림, 검증 없이 결론부터 씀 | — |
| 5 | `impl` 구현 | 위 어느 것도 아닌 AI의 실수(코드·인용·계산) | — |

## 근거 규칙
- 판정마다 **근거 인용**(사람 또는 AI 메시지에서 짧게)과 **턴 번호** 또는 이벤트 시각을 붙인다. 근거가 없으면 판정하지 않는다.
- 후보 파일에 없는 내용은 추측하지 않는다. 판단할 수 없으면 `unknown`.
- 원인 이름은 위 다섯 개와 `unknown`만 쓴다.

## 다음 작업에 돌려줄 것 (원인별로 하나씩 제안)
| 원인 | 형식 | 예 |
|---|---|---|
| `plan_gap` | 다음 목표 정의에서 물을 질문 한 줄 → `.aif/plan-questions.md` | "빈 입력·오류 응답일 때 화면은 어떻게 보여야 하나?" |
| `decision` | 기획 단계에서 미리 정할 결정 항목 | "외부 라이브러리 선택은 승인 전에 정한다" |
| `setting` | 고칠 설정과 위치(코어 배치표 기준) | "확인 명령 `npm test`를 config.commands.test에 넣는다" |
| `process` | 진행 방식 기준 | "화면 3개 이상이면 표준 경로" |
| `impl` | 해당 역할 체크리스트 항목 | "목록 조회 N+1 확인" |

## 출력 형식 (판정자 하나당)
```json
{
  "judge": "A",
  "items": [
    {
      "candidate_id": "k-07",
      "kind": "cause",
      "label": "plan_gap",
      "evidence": [{"turn": 14, "quote": "빈 값이면 어떻게 돼요?"}],
      "suggestion": "빈 입력·오류 응답일 때 화면은 어떻게 보여야 하나?"
    }
  ]
}
```
판정자는 후보 파일과 함께, 후보에 적힌 `goal_doc`과 `evidence_files`(검증 보고 등)를 열어 볼 수 있다. 그 밖의 코드·기록은 보지 않는다.

`kind`는 `prompt`(후보 id `p-…`), `claim`(`c-…`), `cause`(`k-…`) 중 하나입니다. 원인 후보 id는 내용으로 정해진다(`k-rule-<규칙 id>`, `k-eff-verify`, `k-q-first-verify` 등). 분석을 다시 돌려도 같은 후보는 같은 id라 판정이 어긋나지 않는다.

두 판정자의 `label`이 같으면 채택하고, 다르면 `uncertain`으로 합칩니다. `suggestion`은 채택된 항목의 것만 씁니다(두 개가 다르면 둘 다 보이고 사람이 고릅니다).

## 제안이 거스르면 안 되는 것
제안(`suggestion`)은 프레임워크의 고정 항목과 정한 방침을 거스르지 않는다. 거스르는 제안은 다음 작업을 다시 같은 문제로 이끈다.
- 상한(시간·토큰)은 완료 기준이 아니다. 넘으면 멈추고 묻는 신호다. "상한을 완료 기준에 적는다"는 제안을 하지 않는다. 상한 관련 제안은 "값과 재는 방법을 기획 때 정한다" 형태로 쓴다.
- 검증은 독립된 증거로 한다. 검증을 줄이거나 수행 단계가 스스로 판정하게 하는 제안을 하지 않는다.
- 사람 승인 지점(목표 승인, 전달)을 없애는 제안을 하지 않는다.
- 검증자의 Minor·Low 지적은 게이트가 아니라 후속이다.
